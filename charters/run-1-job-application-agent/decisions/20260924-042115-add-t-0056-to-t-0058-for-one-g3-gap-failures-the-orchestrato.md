The previous pass recorded 375 passed, 1 skipped at this HEAD. Reading the scan paths for G3, I found a gap the previous pass missed. The orchestrator catches query-generation, fetch and scoring exceptions and records them only as `error_*` RunReport counters. _empty_scan_explanation (src/bot_service.py:33) reads only `skipped_*` and `rejected_*` counters. CrawlerEngine.search turns a Brave transport failure into [] and records nothing. So an OpenRouter or Brave outage reaches the user as 'no new matching jobs... I could not fetch any job pages this run.' That breaks the G3 definition of done: 'an error during a scan produces a message naming what failed'.

## Decision
Add three small tasks, chained only where files overlap or where a later task needs an earlier one's result. T-0056: render error_ counters, with labels, in the empty-scan message, leaving the existing four branches unchanged. T-0057: record a Brave search failure as error_search_failed via a CrawlerEngine.last_search_error attribute read by the orchestrator. T-0058: a README sentence. All acceptance checks are shell-runnable commands, because T-0048 failed on prose acceptance. Assumptions, taken conservatively: (1) only counts and labels go into the user-facing message, never exception text, to avoid leaking URLs or secrets to real users; (2) the budget-exhausted empty search is not an error; (3) M1–M3 still read 'planned' only because no op can change milestone status.

## Consequences
Once this lands, an empty scan caused by a caught failure names that failure, closing the last G3 gap I could find. The harness metrics are unaffected; T-0056 and T-0057 run the offline_eval check anyway to confirm that. If T-0056 stalls, T-0057 and T-0058 wait on it, but the chain is only two deep. After these merge, return to idle unless a followup or a regression shows a gap. Tim should still mark M1–M3 done in ROADMAP.md by hand.
