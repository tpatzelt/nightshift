# Build the offline harness and freeze the arming baseline before touching any quality logic

_Recorded 20260922-150337 by the NIGHTSHIFT planner._

## Context
Initial planning pass: the backlog, parked list, done list and worker followups are all empty, and the roadmap carries M1-M3 as planned with no tasks attached. The planner sandbox mounts /work and /plan as the same directory (identical device:inode) and contains no checkout of job-application-agent; a filesystem-wide search for url_heuristics.py, crawler_engine.py and run_mock_test.py found nothing. Tasks are therefore derived from the charter text alone, using the file paths the charter names explicitly. The charter defines G2 as an improvement over 'the baseline recorded at arming', measured by the G1 harness, which means no G2 change can be evaluated until the harness exists and a baseline has been captured from unmodified src/.

## Decision
Twelve tasks in strict G1 > G2 > G3 order, chained by depends_on. M1 splits into fixture loader, pure metric functions, replay driver, CLI entrypoint, baseline freeze plus README, and a per-record failure dump. The baseline task (T-0005) protects src/**, so the recorded baseline provably reflects unmodified logic, and it introduces a --compare-baseline mode that exits non-zero on any metric regression; the three M2 tasks then use that command as their acceptance gate, one metric per diff for attributability, with evals/** protected so the harness cannot be tuned to flatter a change. M2 tasks depend on T-0006 so fixes target enumerated failures rather than guesses. The three M3 tasks depend on the dedup work in T-0009 because notification idempotency keys on canonical posting identity. Module and function names (evals.fixtures.load_runs, evals.metrics.*, evals.replay.replay_all, evals.offline_eval) are planner-defined contracts that let the tasks compose without a shared checkout. No milestones were added: M1-M3 already cover G1-G3 one-to-one, and adding more would risk inventing goals.

## Consequences
Assumptions recorded, since the human cannot be asked: (1) the worker sandbox, unlike the planner's, has the repo, and evals/runs/** actually contains recorded search results - T-0001 is instructed to report blocked rather than fabricate fixtures if it does not; (2) the interface names above are invented by this pass and a worker may find a better fit with existing layout, in which case later tasks' acceptance commands need a planner update; (3) every task is status ready with ordering carried by depends_on, because the schema example shows no other status and marking tasks blocked risks a stall with nobody present to unblock them - this assumes the runner honours depends_on. The chain is long and strictly serial, so a block at T-0001 stalls everything; that is accepted because the charter's own priority order and the baseline-before-change requirement make parallelism unsound here. Tasks that write the JSON report cannot protect evals/runs/** wholesale without blocking their own output, so they carry an acceptance check asserting nothing outside evals/runs/offline/ changed. No allowed_paths is a catch-all, the deployment files named as non-goals are protected in all twelve tasks, and the largest max_diff_lines is 400.
