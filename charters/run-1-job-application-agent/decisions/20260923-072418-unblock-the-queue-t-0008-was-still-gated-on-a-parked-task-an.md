## Decision
No new tasks, no new milestones, no scope change - M1-M3 still map one-to-one onto G1-G3 and the ten existing tasks still describe work the code needs. Repair the plan instead. Rank all ten in charter order: T-0011 then T-0012 (G1/M1 re-baselining and corpus growth), then the serial url_heuristics chain T-0013, T-0014, T-0008, then T-0009 (G2/M2), then T-0016, T-0010, T-0015, T-0017 (G3/M3), and issue the matching reorder. Move T-0008 onto T-0014 and T-0009 onto T-0012 as the previous ADR intended, so no ready task depends on a parked one and no task is worked while its metric is saturated. Correct three stale references so allowed_paths and citations match the tree as it is today: canonical_url at :74 not :62, _scan_worker at :218 not :227, and _build_messages not _build_message. Add to T-0009 the verified list of which candidate phrases are genuinely new - 'we are no longer accepting applications for this' is already a substring match under the existing 'no longer accepting applications' entry, so adding it would buy a green test and no behaviour change. Finally, remove `--check-baseline` from T-0012's acceptance gate while requiring the worker to run it and report its exit status and any below-baseline metric in the task output: the baseline T-0012 freezes is computed from arming src, so a corpus that honestly exposes a current-code regression would fail its own gate for a reason the task is explicitly forbidden to fix (corpus softening is banned, src/** is protected there). Measurement is preserved; the gate simply stops punishing a truthful result. All integrity controls from earlier passes are kept unchanged: evals/** protected in every M2/M3 task, src/** protected in both M1 tasks, evals/metrics.py and evals/offline_eval.py protected even in the corpus task, the five deployment non-goals plus CLAUDE.md protected everywhere, no catch-all allowed_paths, largest max_diff_lines still 400.

## Consequences
Assumptions recorded, since nobody can be asked. (1) I read rank as the queue's ordering key and depends_on as the readiness gate; if the runner orders purely by file order or by depends_on, the reorder op is harmless and the dependency fixes still do the real work. (2) Ranking the two independent G3 tasks (T-0016, T-0010) below the six-deep G1/G2 chain follows the charter's stated priority order, at the cost that a single-worker runner which only ever considers the top-ranked task would idle while the chain is blocked; a runner that picks the highest-ranked ready task falls through to T-0016 automatically, which is the intended behaviour. (3) Dropping --check-baseline from T-0012's gate slightly weakens the automatic protection against a corpus that quietly degrades the current code's score. I judged that acceptable because evals/metrics.py, evals/offline_eval.py and src/** are all protected in that task, the baseline is written only by T-0011's arming-revision tool, and the worker must still print the check's result - so any regression is recorded in the output and reaches the next planning pass rather than being hidden. (4) If T-0012 does reveal a metric where current src scores below arming, every downstream M2 task's --check-baseline acceptance fails until it is fixed; I deliberately did not pre-emptively add a fix task, because its content cannot be known before the corpus exists and inventing one would be speculative work. The next pass, which runs after T-0012 reports, adds it if needed. (5) Parked T-0007 stays parked and is not revived: its approved diff is absent from the tree and its content is fully re-issued as T-0013 and T-0014, so reviving it would risk two workers writing the same vendor branches.
