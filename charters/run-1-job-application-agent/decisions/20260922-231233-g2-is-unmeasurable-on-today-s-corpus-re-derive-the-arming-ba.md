# G2 is unmeasurable on today's corpus: re-derive the arming baseline from the arming revision and grow the corpus before any more quality work

_Recorded 20260922-231233 by the NIGHTSHIFT planner._

## Context
Fourth planning pass, with /repo/job-application-agent read before writing. M1 is effectively delivered (T-0001..T-0005 done: corpus loader, metrics, replay driver, frozen baseline with --check-baseline, README). The decisive new finding is arithmetic: evals/baseline.json records posting_shape_rate 0.750, aggregator_drop_rate 1.000, location_match_rate 1.000, staleness_detection_rate 1.000, dedup_rate 0.750 over 23 records. The charter's G2 definition of done demands improvement on at least posting-shape AND aggregator-drop rate; aggregator-drop is already saturated, so G2 cannot be met on this corpus no matter what code is written. I verified this rather than assumed it: running the current harness gives delta +0.000 on all five metrics, and replaying the same corpus against src/ materialised from the arming commit b6da8dd ('wip: baseline for nightshift', the merge-base with origin/main) reproduces the frozen baseline exactly - so T-0006, the aggregator-host widening that is marked done, provably moved no metric. Per-record inspection shows where the remaining headroom sits: the three kept /careers listing pages are the whole posting_shape gap, and one labelled duplicate pair (www+https vs bare+http on jobs.lever.co) is the whole dedup gap. Second finding: parked T-0007 carries a reviewer 'approve' at attempt 2, but its code is absent from the tree (no bamboohr/teamtailor branch in _ats_kind) and HEAD is T-0006, so that work was lost, not merged - and T-0008 depended on it, which would have stalled the dedup work behind a parked task. Third: the G3 gaps named in the earlier ADR are still real in the code - _format_result drops JobResult.reason, _notify discards notify_results' bool while the seen-URL cache is saved before notification, _scan_worker sends one fixed error line naming nothing, and tests/test_bot_service.py asserts no message text at all.

## Decision
Put two G1/M1 tasks in front of all remaining G2 work. T-0011 adds evals/rebaseline.py, which materialises src/ from a git revision with `git archive`, runs the current evals package against it in a temp directory, and prints or writes the resulting baseline; I ran that exact procedure by hand and it reproduces the committed baseline, so the task's core test is a known-good assertion rather than a guess. T-0012 then grows the corpus with the shapes the code actually gets wrong - unknown ATS vendors, digit-shaped non-postings like /careers/2024/, index pages on the hosts T-0006 added, near-duplicates differing only by scheme/www/query order, and postings closed with wordings STALE_PHRASES misses - sourced where possible from a small budgeted set of live Brave searches as the charter invites, hand-labelled, and re-freezes evals/baseline.json using T-0011's tool AT THE ARMING REVISION. Computing the baseline from arming code rather than from the current tree is the integrity crux: it gives T-0006 the aggregator-drop credit it earned, creates honest headroom on the charter's second must-improve metric, and makes it impossible to manufacture an improvement by re-recording after the fact. The parked T-0007 work is re-issued as T-0013 (ten ATS vendors) and T-0014 (year and page-number segments), split so each half is small after two failed attempts, and both are gated on the expanded corpus. T-0008 moves off the parked dependency onto T-0014, keeping url_heuristics.py edits serial; T-0009 moves onto T-0012 because its metric is saturated until then. Three G3 tasks complete M3: T-0016 (scan errors that name the failure, with secret scrubbing, independent so it can start immediately), T-0015 (a delivered-postings ledger inside TelegramNotifier, keyed on canonical_url and written only after a send actually succeeds, depending on T-0008 so it is built on the final key shape), and T-0017 (assert the content of the remaining message paths, tests only, src/** protected). No milestone was added - M1-M3 still map one-to-one onto G1-G3. Integrity controls kept from earlier passes: evals/** protected in every M2/M3 task, src/** protected in both M1 tasks, evals/metrics.py and evals/offline_eval.py protected even in the corpus task so the corpus cannot be grown by changing what is measured, the five deployment non-goals plus CLAUDE.md protected everywhere, no catch-all allowed_paths, largest max_diff_lines 400.

## Consequences
Assumptions recorded, since nobody can be asked. (1) 'The baseline recorded at arming' is read as 'what the arming-revision code scores on whatever corpus the harness replays', not 'the literal numbers in today's baseline.json'. That is the only reading under which G2 is achievable and under which growing the corpus is honest; the alternative reading makes G2 unreachable by construction. Re-freezing baseline.json is therefore a deliberate, tool-mediated act, not a re-record from improved code, and T-0012 must quote the arming-vs-current delta in its output so the change is auditable. (2) Expanding the corpus may reveal that current code scores BELOW arming on some metric - most plausibly a T-0006 aggregator host swallowing a legitimate employer page. T-0012 is told to keep such records, report them, and not soften the corpus; the cost is that --check-baseline could then fail for every downstream M2 task until the regression is fixed, which is the correct failure mode but will cost iterations. (3) The three /careers listing pages are the whole posting_shape gap today, and the honest way to close it is more corpus, not dropping listings from the kept set - listings are harvested for links in production, and narrowing the harness's kept set to raise a score would be gaming it. That option is closed off by protecting evals/offline_eval.py in T-0012 and evals/** in every M2 task. (4) T-0011's tool shells out to git and so depends on repository history; if a worker's checkout lacks .git or the arming commit (it is a local, unpushed commit also reachable as origin/tp/nightshift-base), the tool exits with a message and its test skips rather than failing, which keeps the suite green at the cost of the baseline not being re-derivable in that environment - a worker hitting it should report blocked. (5) T-0007's approved-but-lost diff is treated as not done; re-issuing it as two tasks risks duplicating work if that diff resurfaces, which is the cheaper error than leaving a charter-named metric unimproved. (6) Live Brave calls in T-0012 spend Tim's quota; the task is capped to a small number of searches, forbidden from looping, and required to leave fixtures behind so no later agent pays again - and forbidden, as everywhere, from writing a key into any file. (7) The chain is serial through T-0011 to T-0014 because each step's measurability depends on the previous one; T-0016 and T-0010 branch off immediately as independent G3 work so a stall in the G2 chain does not idle the queue.
