# Ground the backlog in the real repo: the G1 corpus is absent, so it must be authored as a committed labelled fixture set

_Recorded 20260922-151055 by the NIGHTSHIFT planner._

## Context
This is the third planning pass and the first with the code actually visible: /repo/job-application-agent is mounted read-only and was read before writing tasks. The two earlier passes (ADRs 20260922-150203 and 20260922-150337) planned blind, explicitly assumed the charter's file paths and corpus existed, and left nothing behind - the backlog is still 0 ready and /plan/backlog holds only EXAMPLE.yaml.txt. Their task sets are superseded rather than merged, because several of their invented interfaces do not match the layout on disk. The decisive finding: G1 says the harness replays 'the recorded search results in evals/runs/**', but evals/runs/ is listed in .gitignore at line 221, has never appeared in git history (checked with git log --all over that path), and does not exist in the mount. There is no recorded corpus. Recording a real one needs Brave, which the charter puts out of scope by construction. Everything else the charter names does exist and was read: src/url_heuristics.py, src/page_signals.py, src/crawler_engine.py, src/orchestrator.py, src/notifier.py, src/telegram_api.py, src/bot_service.py, plus an existing online eval package (evals/checks.py, run_eval.py, recheck.py, compare.py, profiles.py) whose scoring is welded to a requests.get and so is unreachable offline. Concrete defects the tasks target were read out of the code, not guessed: AGGREGATOR_HOSTS holds 13 hosts; _has_posting_id counts any 3+ digit segment as a job ID so /careers/2024/ is a posting; canonical_url ignores scheme, www. and query order; TelegramNotifier._format_result never prints JobResult.reason; Orchestrator._notify discards notify_results' success bool and has no ledger beyond cache.json; _scan_worker sends one fixed error line naming nothing.

## Decision
Thirteen tasks, ordered G1 > G2 > G3, chained by depends_on, every one citing one goal and one milestone. No milestones added - M1-M3 already map one-to-one onto G1-G3 and more would risk inventing goals. On the missing corpus, the conservative reading that stays inside the charter is that G1's harness is the deliverable and its input must be authored offline: T-0001 commits a hand-labelled corpus as JSONL under evals/fixtures/ (a new path, because anything under the gitignored evals/runs/ would not survive a clean checkout and the 'exits 0' definition of done would be unreachable), while the harness keeps a --corpus flag so a real recorded run under evals/runs/<tag>/ can be replayed if one ever exists. evals/runs/offline/ stays the output location exactly as the charter specifies; .gitignore is untouched. Labels are hand-assigned ground truth and must not be generated from the functions under test, or the metric tests are vacuous and G2 improvement is unmeasurable. T-0002 splits evals/checks.py into a pure score_page plus a fetching check_result, so the offline harness reuses one copy of the scoring rules and the existing online eval keeps working - reuse rather than a parallel implementation. T-0003's replay imports the deterministic functions from src/ instead of reimplementing them, so the harness measures the code G2 changes. Integrity controls: evals/** is protected in every M2 and M3 task, so no worker can raise a score by editing metrics, corpus or baseline; T-0004 protects src/** so the frozen baseline provably describes unmodified logic; the five deployment non-goals plus CLAUDE.md are protected in all thirteen tasks; no allowed_paths is a catch-all and the largest max_diff_lines is 400, well under the 800 ceiling. The four M2 tasks each move one metric and all gate on the same `--check-baseline` command, which fails on any regression - that is what stops an aggregator sweep from buying aggregator_drop_rate with posting_shape_rate.

## Consequences
Assumptions recorded, since the human cannot be asked. (1) Authoring a synthetic labelled corpus is treated as in-charter fixture work, not as stubbing a blocked API; it introduces no dependency, makes no network call, and contains no personal data. The cost is that G1 and G2 measure quality on a corpus this system wrote, so the absolute numbers describe the corpus as much as the agent - the metrics are valid for comparing changes, not for claiming real-world accuracy, and the README task says so. (2) If a worker's checkout does contain real recordings under evals/runs/**, T-0001 should prefer them and report a followup; the JSONL schema was chosen to mirror what evals/run_eval.py already writes per result. (3) T-0004 may find the baseline already at 1.0 on a named must-improve metric, which would make G2 unachievable on this corpus; the task is told to report that as a followup rather than weaken a metric, and the next planning pass would add a harder-records task. (4) T-0008 changes canonical_url, so existing on-disk cache.json files stop matching and one run may re-check some already-seen postings; T-0011 depends on T-0008 precisely so the notification ledger is built on the final key shape, and the two together keep that cache churn from turning into duplicate notifications. (5) All tasks are status ready with ordering carried by depends_on and the reorder op, assuming the runner honours depends_on; marking tasks blocked would risk a stall with nobody present to unblock them. (6) The chain is long and mostly serial through M1 because the charter defines G2 against a baseline only T-0004 can produce; T-0009, T-0010 and T-0012 branch off T-0004 in parallel to soften that, since they touch disjoint files.
